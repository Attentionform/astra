# ASTra benchmark protocol (pre-registered)

Status: **work in progress.** ASTra changes every day, so every number produced by this suite
belongs to one named release. Nothing here is a permanent claim about the product.
This file was committed **before** the first measurement was run. Any later change to it is
listed in the "Deviations" section at the end, with the reason and the date.

## 1. Purpose and scope

Measure what the published ASTra packages do, with methods a third party can repeat.
The suite covers six questions:

| # | Question | Experiment |
|---|----------|------------|
| Q1 | Can an agent **create** valid Word documents, and at what cost? | C1, C2 |
| Q2 | What does an agent pay to **read** a document? | R1 |
| Q3 | Does an **edit** touch only what it should, and is the result valid? | E1 |
| Q4 | Does the **schema gate** stop invalid documents without false alarms? | E3 |
| Q5 | Are batches **atomic** and is **history/revert** exact? | E4, E5 |
| Q6 | How do latency and memory **scale** with document size? | E6, E7 |

Out of scope for this release: comparison with other products, rendering fidelity in Microsoft
Word (a manual protocol is described in section 9 and its results are reported separately),
and end-to-end agent success rates (section 10, planned, not run).

## 2. System under test

* Exactly the npm packages `@attentionform/astra-mcp-server@0.4.1` and its pinned
  dependencies, installed by `npm ci` from `benchmarks/package-lock.json` into `benchmarks/node_modules`.
* All calls go through the **public MCP interface** (stdio, the 19 published tools), the same
  surface an AI assistant uses. No private imports, no test hooks.
* Environment (OS, kernel, CPU model, core count, RAM, Node, LibreOffice, Python and library versions,
  npm integrity hashes of every ASTra package) is captured by `run/env.mjs` into `results/<release>/env.json`.

## 3. Corpus

All documents are **generated by this repository's scripts** from fixed seeds. No customer or
private document is used. The corpus is produced by independent writers so it does not only contain
ASTra-shaped files:

| Writer | Role | Content |
|--------|------|---------|
| python-docx 1.2.0 | independent producer | prose reports, table-heavy, list-heavy, mixed (headings, tables, lists, images, header/footer), comments |
| LibreOffice 25.2 (HTML to DOCX) | independent producer | prose, tables, lists, styled text |
| XML injection (lxml) | feature coverage | tracked insertions and deletions, bookmarks, hyperlinks |

Size ladder: 1, 2, 5, 10, 25, 50, 100 and 200 pages (page count is measured by LibreOffice PDF export,
not assumed). Target: at least 40 documents. `corpus/manifest.json` lists every file with writer,
seed, size in bytes, SHA-256, paragraph/table/image counts and measured page count.
Corpus files are not committed (`*.docx` is ignored); `npm run corpus` regenerates them.

## 4. Experiments

### C1 Create from Markdown (create pillar)

Input: 24 Markdown specifications from a seeded generator (headings 1 to 4, paragraphs with bold,
italic, code and links, bullet and numbered lists up to 3 levels, tables up to 12 columns, block quotes,
code blocks), sized 1 to 100 pages.
Procedure per spec: `new_document` (blank) then `compose_document` then `save_document`.
Repeat with each template (`report`, `memo`, `blank`).
Metrics:

* success rate and error codes
* gate verdict and independent oracle results (section 5)
* **content fidelity**: fraction of source blocks found in the output, in order, with matching text,
  heading levels, list nesting and table shape (computed by an independent reader, not by ASTra)
* **writing cost**: tokens in the Markdown source versus tokens of the `word/document.xml` an agent
  would have had to write to get the same document (ratio, per document)
* wall time by size

### C2 Create with typed operations

Fifteen fixed recipes, each built from an empty document with `execute_batch`:
styled headings, paragraph formatting, bullet and numbered lists, table with merged cells,
table with header row styling, inline image, callout, chart, equation, footnote, header and footer,
page setup and columns, section break, hyperlink, comment.
Per recipe: pass or fail, oracle results, error code on failure. Failures are listed, not averaged away.

### R1 Representation cost (read path)

For every corpus document: bytes and tokens of `word/document.xml`; bytes and tokens of the
`inspect_document` outline at `compact`, `standard` and `full` fidelity; ratio per document.
Tokenizer: `o200k_base` through `gpt-tokenizer` 3.0.1. This is a **proxy**: no Claude tokenizer is
available offline, so absolute counts differ by model; ratios are the quantity of interest.
Report median, interquartile range and bootstrap 95% CI, by size bucket and by writer.
This experiment also checks the README sentence "roughly 5x fewer tokens than raw XML on our demo report".

### E1 Edit correctness and locality

Eight edit types: replace paragraph text, restyle one word (`match`), insert paragraph after a node,
delete a paragraph, replace a table cell, add a comment, tracked replace, change paragraph style.
For each document and edit type, 4 target positions (first, middle, last, one seeded random).
Procedure: open, apply the edit, save, then compare the saved package with the original:

* package parts changed (names) and bytes changed
* paragraphs whose XML changed **other than the target** (expected 0)
* text of all non-target paragraphs unchanged (expected 100%)
* the edited paragraph shows the intended change (read back by an independent parser)
* no-op baseline: open then save with no edit, to measure churn that is not caused by the edit

Control (no product named): the same document is parsed and re-serialized with plain `lxml` and written back
to a zip. This shows how much churn a generic parse-and-reserialize step causes on the same corpus.

### E3 Schema gate efficacy (fault injection)

* **Faults.** 60 fault specifications across six categories: element order, attribute values
  (enumerations, ranges, patterns), unknown elements and attributes, missing required children,
  duplicate or invalid identifiers, and dangling relationships. Each category has 10 specifications.
  Each is applied by XML mutation to 3 base documents (one per writer), giving 180 injected files.
  A mutation is labelled "invalid" by construction from the ECMA-376 rule it breaks.
* **Negative controls.** 20 valid mutations (for example reworded text, extra run properties from the schema)
  and every clean corpus document, to measure false alarms.
* **Measurements.** `validate_document` verdict; `save_document` in default mode and in strict mode
  after a trivial edit; whether bytes were written to disk when the verdict was "invalid".
* **Metrics.** detection rate per category with Wilson 95% CI; false-alarm rate with CI;
  invalid files written to disk by default mode and by strict mode; list of every missed fault.
* Note: the detector inside ASTra is Microsoft's Open XML SDK validator. This experiment measures the
  integrated behaviour (routing, refusal, nothing written), and also lists which fault classes the upstream
  validator does not detect. It does not claim to improve on that validator.

### E4 Atomicity

120 trials: batch sizes 2, 5, 20, 100; the failing operation placed first, in the middle, last;
four failure kinds (unknown target, schema-invalid parameters, unknown style, absent text match).
After the failed call: outline hash, revision number, dirty flag and a forced save compared with the state before.
Metric: share of trials with zero residual change.

### E5 History and revert

30 sequences of 10 saved edits on 10 documents with 3 seeds. After every save: SHA-256 of the file and of
`word/document.xml`. Then `preview_revert` and `revert_document` to every earlier commit, and `redo_document`.
Metrics: byte equality of restored content with the recorded hash; accuracy of the preview file list versus the
actual change; redo restores the head exactly; growth of the history store per save on 3 document sizes over 50 saves.

### E6 Latency and memory by size

Sizes 1, 10, 50, 100, 200 pages. Operations: open, inspect (standard), search, single replace,
50-operation batch, validate, save. 15 timed runs after 2 warm-up runs, plus 1 cold run reported separately.
Report median, p95, min, max, coefficient of variation, n. Server resident memory peak sampled from `/proc`.
Validator share of save time = validate time / save time.

### E7 Batch scaling

Batches of 1, 10, 50, 100, 250, 500 operations on a 50-page document, 10 runs each.

## 5. Independent oracles

Every file written by C1, C2, E1 and E5 is checked by oracles that are not ASTra code:

| Oracle | Check |
|--------|-------|
| O1 | ZIP integrity: CRC valid, no duplicate entries |
| O2 | Every XML part is well-formed (lxml) |
| O3 | Every relationship target exists; every part has a content type |
| O4 | LibreOffice headless opens it and exports a non-empty PDF (exit code 0) |
| O5 | An independent reader (python-docx 1.2.0) loads it and iterates all paragraphs and tables |
| O6 | Microsoft Open XML SDK validator through `validate_document` (reported separately, it is the gate) |

A file passes only if O1 to O5 all pass. O6 is reported next to them.

## 6. Statistics

* Rates: Wilson score 95% interval. Zero failures out of n is reported as "0/n, upper 95% bound x%".
* Timings and ratios: median, p25, p75, p95, min, max, n; bootstrap 95% CI of the median (10,000 resamples, seed 20261111).
* No outliers removed. Failed runs are counted and published.
* Timings come from one machine and one run session; the suite repeats on request, results are per release folder.

## 7. Pre-registered expectations

These are written before measurement. They are expectations, not promises; a miss is published as a miss.

| ID | Expectation |
|----|-------------|
| H1 | Median `standard` outline is at least 3x smaller in tokens than `document.xml` (README says "roughly 5x" for one demo document; the corpus median may differ) |
| H2 | 0 non-target paragraph changes in all E1 trials |
| H3 | 100% of produced files pass O1 to O5 |
| H4 | Gate detects at least 95% of injected faults, with 0 false alarms on clean and valid-mutation controls |
| H5 | 100% atomic outcomes in E4 |
| H6 | 100% byte-exact restores in E5 |
| H7 | Median save time under 5 s for a 100-page document |
| H8 | C1 content fidelity at least 98% of blocks; every created file passes O1 to O5 |

## 8. Threats to validity

* Synthetic corpus: realistic structure, but not real-world mess. A private real-document corpus exists; it is
  not published and no result from it appears in this suite.
* Author-designed faults: the fault list is written by the project. It is published in full so others can add faults.
* One machine, one OS (Linux on WSL2 for this release). Windows and macOS runs are future work.
* Tokenizer proxy: see R1.
* The gate and the detector are the same component for E3; independent confirmation of the fault labels
  comes from the ECMA-376 rule each fault breaks, not from a second validator.
* LibreOffice is lenient; passing O4 does not prove Word opens a file (see section 9).

## 9. Word compatibility check (manual, reported separately)

A fixed sample of 30 output files (stratified over C1, C2, E1) is opened in Microsoft Word on Windows.
Recorded per file: opens without repair prompt (yes/no), page count, screenshot hash. Results go to
`results/<release>/word-manual.csv` with the Word build number. Not part of automated pass rates.

## 10. Planned, not yet run: agent end-to-end

15 tasks (create 5, edit 7, repair 3), 10 runs per task per model, success judged by a script against
a checklist, 95% CIs, tool-call counts and token totals. Needs model access and budget; protocol only for now.

## 11. Reproduction

```bash
cd benchmarks
npm ci
npm run env        # record environment
npm run corpus     # generate corpus + manifest
npm run all        # run every experiment, write results/<release>/
npm run report     # build results/<release>/REPORT.md from raw data
```

Raw per-trial data (`*.jsonl`) is published with the summaries. Nothing is dropped.
